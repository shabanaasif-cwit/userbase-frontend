# v0.1.8 - 2026-04-07

(D) 2026-04-07

### Added

- No user-facing additions in this release.

### Changed

- Admin account status updates (`updateUserStatusAPI`) now call the dedicated routes first—`PATCH /api/users/{id}/deactivate` to deactivate and `PATCH /api/users/{id}/toggle-account` to reactivate—then fall back to `PATCH /api/users/{id}` with `{ status, isActive }` if those routes fail. This matches backends that persist account state on the action endpoints and avoids treating a successful generic PATCH as saved when the server ignores unknown fields such as `status`.

### Fixed

- Saving **Account status** from the admin **Edit user** dialog (and the row-level activate/deactivate controls) now aligns with database-backed account state more reliably when the user PATCH handler applies `role` but not `status`.
- **Role** and **Account status** dropdowns in the edit-user dialog use the same dark native-select styling as the admin filter row so the selected value stays readable when the control is closed.

### Security (if applicable)

- No security-specific changes in this release.

### Internal

- Reworked `updateUserStatusAPI` in `app/lib/auth-context.tsx` (call order, fallback body including `isActive`, and inline documentation of the “200 but ignored field” pitfall).
- Set `data-native-dark` on the edit dialog’s role and account-status `<select>` elements in `app/admin/users/page.tsx`.
