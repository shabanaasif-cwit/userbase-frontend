# v0.1.9 - 2026-04-08

(D) 2026-04-08

### Added

- `app/lib/notification-read-persistence.ts`: shared client helpers to store read notification ids per signed-in user (email-keyed `localStorage`) and merge that state with API results.

### Changed

- **Header** notification list and badge treat notifications as read when their ids appear in persisted read storage, in addition to the API `isRead` flag, so the UI stays consistent after refetches and navigation.
- **`/notifications`** uses the same merge-and-persist flow when loading, opening an item, or marking all read, so behavior matches the header for both regular users and admins viewing their inbox.

### Fixed

- Notifications marked read no longer reliably reappear as “new” or inflate the unread count when the list is reloaded, the route changes, or the user signs in again on the same browser (when the API omits or resets read state).

### Security (if applicable)

- Read-notification ids are stored in the browser `localStorage` keyed by normalized email; on a shared device, clearing site data or using a private window limits exposure. No server-side auth model changes.

### Internal

- `app/component/header.tsx` and `app/notifications/page.tsx` import `mergeWithPersistedReadState` and `persistReadNotificationIds` from `@/lib/notification-read-persistence` instead of duplicating storage logic.
